# ⛅ Distributed Weather Forecast Aggregation System
**Spring Boot + RabbitMQ + OpenWeatherMap API**

## 💻 Описание проекта
В рамках лабораторной работы была разработана распределенная система для агреграции погодных данных, основанная на микросервисной архитектуре.
Каждый сервис выполняет отдельную роль в процессе получения, обработки и объединения прогнозов погоды для заданных городов.

Система реализует **паттерн Aggregator** и взаимодействует через **RabbitMQ** как брокер сообщений.
В качестве источника данных используется **OpenWeatherMap API**.

## ⚙️ Архитектура системы
Проект состоит из 4 основных компонетов:
### 1. **weather-api-service**
- Принимает запросы от фронтенда через REST API.
- Отправляет задачи в очередь `weather.request.queue` через RabbitMQ.
- Ожидает и агрегирует ответы от других сервисов.
- Использует асинхронную обработку с помощью `CompletableFuture`.

### 2. **weather-consumer-service**
- Получает сообщения с запросами на прогноз погоды.
- Делает HTTP-запрос к **OpenWeatherMap API** для каждого города.
- Формирует ответ и отправляет его обратно в очередь `weather.response.queue`.
- Использует ручное подтвеждение доставки сообщений (`manual ACK`).

### 3. **weather-aggregator-service**
- Реализует паттерн **Aggregator**.
- Собирает все частичные ответы по `correlationId`.
- После получения всех данных формирует сводный отчет и отправляет его в очередь `weather.aggregated.queue`.
- Имеет планировщик (`@Scheduled`) для очистки устаревших процессов агрегации.

### 4. **weather-frontend**
- Простой одностраничный интерфейс на HTML, CSS и JavaScript.
- Позволяет ввести список городов и отправить запрос к API.
- Отображает результаты в виде таблицы.
- Работает с REST-endpoint

## 🧾 Контрольные вопросы

1. **В чем основное преимущество использования брокера сообщений по сравнению с прямым REST-вызовами между сервиса?**

Брокер сообщений (RabbitMQ) обеспечивает **ассинхронное взаимодействие**, независимость сервисов и устойчивость при временных сбоях.
Rest-вызовы требуют постоянного соединения и синхронного отклика, что делает систему менее гибкой и устойчивой к отказам.

2. **Что такое Correlation ID и какую роль он играет в паттернах Request-Reply и Aggregator?**

CorrelationId - это идентификатор, который связывает исходный запрос и его ответы.
В паттерне **Request-Reply** он позволяет определить, к какому запросу относится ответ, а в **Aggregator** используется для объединения всех ответов, относящихся к одному запросу.

3. **Опишите, что такое **Completion Strategy** в паттерне Aggregator. Какая стратегия была использована в данной лабораторной работе?**

**Completion Strategy** определяет, **когда агрегатор должен завершить сбор данных и отправить итоговый результат**.
В данной лабораторной работе использована стратегия по **количеству полученных ответов** - агрегатор завершает сбор, когда все ожидаемые ответы для данного `correlationId` получены.

4. **Зачем в weather-consumer-service используется ручное подтвеждение сообщений (manual acknowledgment)?**

Это гарантирует, что сообщение будет считываться обработанным **только после успешного получения данных с API и отправки ответа**.
Если произойдет ошибка, сообщение можно вернуть в очередь для повторной обработки.

5. **Что произойдет, если один запрос к OWM API завершится с ошибкой? Как система обработает эту ситуацию?**

В случае ошибки сообщение будет **отклонено (`basicNack)** и RabbitMQ попытается доставить его повторно.
Это предотвращает накопление "зависших" записей и утечку памяти в длительной работе сервиса.
